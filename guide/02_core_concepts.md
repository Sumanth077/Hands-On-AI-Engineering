# 02. 핵심 개념과 구조

## 공통 파이프라인

대부분의 프로젝트는 다음 경계를 조합한다.

```text
사용자 입력
  → 입력 검증·정규화
  → 검색 또는 도구 선택
  → 외부 시스템 호출
  → 모델 추론
  → 구조화·근거·정책 검증
  → 사용자 출력 또는 승인된 부작용
```

각 경계에서 입력·출력 스키마와 실패 처리 방식을 명시하면 프레임워크가 달라도 시스템을 이해할 수 있다.

## RAG

RAG는 모델이 답하기 전에 관련 자료를 검색해 문맥으로 제공한다.

1. **수집**: 문서, 웹, DB와 미디어를 가져온다.
2. **파싱·청킹**: 의미가 유지되는 작은 단위로 나눈다.
3. **색인**: BM25, 임베딩 또는 지식 그래프로 검색 가능하게 만든다.
4. **검색·재순위화**: 질문에 관련된 근거를 고른다.
5. **생성**: 근거 안에서 답하고 출처를 표시한다.
6. **평가**: 검색 재현율, 답변 충실성과 인용 정확도를 측정한다.

검색 실패와 생성 실패를 분리해야 한다. 좋은 답이 나오지 않을 때 모델만 바꾸기보다 관련 문서가 검색됐는지 먼저 본다.

## 에이전트

에이전트는 모델이 목표를 위해 도구를 선택하고 결과를 관찰하며 다음 행동을 정하는 반복 구조다.

- **상태**: 목표, 대화, 관찰 결과와 남은 예산
- **정책**: 허용 도구, 금지 행동, 승인 조건과 중단 규칙
- **도구**: 검색, 파일, SQL, 브라우저와 외부 API
- **루프**: 계획 → 행동 → 관찰 → 종료 판단

모델의 프롬프트만으로 권한을 강제하지 않는다. 파일 삭제, 이메일 발송, 결제, 예약 같은 작업은 실행 계층에서 허용 목록과 사용자 승인을 검사한다.

## 멀티에이전트

역할을 여러 에이전트로 나누면 전문화와 병렬 처리가 가능하지만 호출 비용, 문맥 손실과 책임 경계가 늘어난다. 역할마다 고유한 입력·출력 계약이 있을 때만 분리하고, 단순 순차 프롬프트라면 하나의 워크플로로 유지하는 것이 낫다.

## OCR과 멀티모달

텍스트만 추출하면 표, 배치와 이미지 의미가 사라질 수 있다. 시각 문서 처리에서는 다음을 함께 평가한다.

- 페이지 렌더링 해상도와 회전·노이즈 처리
- 텍스트, 좌표, 표와 읽기 순서
- JSON schema 같은 구조 검증
- 원본 영역으로 돌아갈 수 있는 provenance
- 의료·금융 문서의 개인 정보 마스킹

## 음성 파이프라인

음성 시스템은 보통 음성 활동 감지, 음성 인식, 언어 처리, 음성 합성으로 구성된다. 실시간 시스템에서는 정확도뿐 아니라 첫 응답 지연, 끼어들기, 잡음, 동시 통화와 실패 시 사람에게 넘기는 경로가 중요하다.

## 파인튜닝

파인튜닝은 프롬프트로 해결하기 어려운 일관된 행동이나 도메인 패턴을 모델에 학습시키는 방법이다. 학습 전에 강한 baseline을 만들고, 학습·검증·테스트 데이터를 분리하며, 데이터 중복과 오염을 검사한다. 모델 품질뿐 아니라 추론 비용, 지연 시간과 안전성 회귀도 비교한다.

## 공급자 독립 설계

모델 호출을 애플리케이션 로직과 분리해 입력 메시지, 구조화 출력, 오류와 사용량을 공통 인터페이스로 감싼다. 공급자를 바꿀 때 확인할 항목은 모델 이름만이 아니다.

- 도구 호출 schema와 스트리밍 형식
- context window와 출력 한도
- 재시도 가능한 오류와 rate limit
- 이미지·오디오 입력 형식
- 데이터 보존 정책과 리전
- 토큰 계산과 가격
