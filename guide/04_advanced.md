# 04. 전문가 수준 설계

## 평가 체계

프로덕션 평가는 단일 정답률로 충분하지 않다.

- **품질**: 작업 성공률, 정확성, 충실성, 인용 정확도
- **검색**: recall@k, precision@k, MRR와 빈 검색 비율
- **에이전트**: 도구 선택 정확도, 완료 단계 수, 승인 위반과 복구율
- **운영**: p50/p95 지연, 오류율, 가용성과 동시 처리량
- **경제성**: 요청당 입력·출력 토큰, 도구 비용과 캐시 적중률
- **안전성**: prompt injection 성공률, 민감 정보 노출과 권한 우회

오프라인 평가셋으로 변경을 빠르게 비교하고, 온라인에서는 사용자 피드백과 실제 실패를 수집한다. 모델·프롬프트·검색 인덱스·도구 버전을 함께 기록해야 결과를 재현할 수 있다.

## 관측성

하나의 요청에 trace ID를 부여하고 다음 span을 연결한다.

```text
request
├─ validation
├─ retrieval
│  ├─ embedding
│  └─ vector_search
├─ model_generation
├─ tool_call
└─ output_validation
```

로그에는 원문 비밀값이나 개인 정보를 넣지 않는다. 프롬프트 전문 보존이 필요하면 접근 통제, 암호화와 보존 기간을 정한다. 토큰 사용량, 모델명, 지연, 재시도와 종료 이유는 구조화 필드로 기록한다.

## 보안

- 검색 문서와 웹 콘텐츠를 명령이 아니라 신뢰할 수 없는 데이터로 취급한다.
- 모델이 생성한 SQL, shell, URL과 파일 경로를 실행 전에 검증한다.
- 읽기와 쓰기 권한을 분리하고 기본값을 최소 권한으로 둔다.
- 외부 전송, 삭제, 구매와 게시에는 사람의 명시적 승인을 요구한다.
- 테넌트별 데이터와 벡터 인덱스를 격리한다.
- 출력 schema 검증 뒤에도 의미상 허용된 값인지 도메인 규칙으로 검사한다.

## 신뢰성

재시도는 timeout과 일시적 rate limit처럼 재시도 가능한 오류에만 적용하고 지수 backoff와 jitter를 사용한다. 동일 외부 작업이 중복되지 않도록 idempotency key를 둔다. 모델 공급자 장애에 대비한 fallback은 품질과 데이터 정책이 동등한지 검증한 뒤 사용한다.

에이전트에는 최대 단계, 최대 시간, 최대 비용과 같은 예산을 둔다. 같은 도구·인자 반복을 감지하고, 불확실하거나 승인 대기 중이면 안전하게 중단한다.

## 비용과 성능

먼저 측정한 뒤 최적화한다.

- 고정 system prompt와 공통 문맥의 cache 활용
- 검색 단계에서 불필요한 문맥 제거
- 쉬운 분류·추출 작업에 작은 모델 사용
- 독립 작업의 제한된 병렬화
- streaming으로 체감 첫 응답 시간 단축
- batch API가 적합한 비동기 작업 분리

비용 절감이 검색 누락이나 안전성 저하를 만들지 않는지 평가셋으로 확인한다.

## 배포

개발 환경과 운영 환경의 모델·프롬프트·인덱스를 버전화한다. health check는 웹 서버가 살아 있는지만 보지 말고 필수 저장소와 모델 endpoint 연결을 구분해 보여준다. 배포는 작은 트래픽부터 시작하고 품질·비용·오류 지표가 기준을 넘으면 자동 중단하거나 롤백한다.

## 기여 경로

1. `CONTRIBUTING.md`와 `.github/README_TEMPLATE.md`를 읽는다.
2. 중복 여부를 검색하고 먼저 issue를 연다.
3. 적절한 카테고리에 `snake_case` 프로젝트 폴더를 만든다.
4. 문서, 의존성 파일, `.env.example`, 실행 코드와 가능한 테스트를 포함한다.
5. 실제 비밀값과 불필요한 생성물을 제거한다.
6. 깨끗한 환경에서 설치와 최소 실행을 재현한다.
7. 한 프로젝트만 포함한 pull request를 제출한다.

## 다음 학습 경로

- OpenTelemetry 기반 trace와 운영 대시보드를 구성한다.
